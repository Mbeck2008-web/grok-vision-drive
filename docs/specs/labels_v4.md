### 2. Obstacles / drivable space

**Source.** Training-only depth and annotation already decode when a camera has `train_gt: true`: uint16 centimetres in `raw/<cam>_depth`, uint8 class ids in `raw/<cam>_sem`, names in `sem_classes.json` (`python/data/raw_frames.py:538-541`, `python/data/raw_frames.py:584-641`, `python/sensors/cameras.py:753-770`). The collector copies those planes onto the tick and writes `sem_classes.json` once (`scripts/collect_scene_lanes.py:2755-2766`). Attach passes `rgb_only=True` and `train_gt=bool(spec.get("train_gt"))` (`scripts/collect_scene_lanes.py:3570-3573`). `config/cameras.yaml:71` is `train_gt: true`, so a new main recording contains depth and semantics.

**Derivation.** Walls, trees, poles, barriers, guard rails, and cones are **unproven**, not known-absent: no annotation palette is on hand. Fine-class labels for those names stay **blocked until palette proof**. Do not reuse `drivable_mask_from_sem` as “everything else is blocked.” That helper is an allowlist of paved names (`ROAD`, `Asphalt`, `ASPHALT`, `Highway`, `HIGHWAY`) and leaves every other id at 0 (`python/train/sensor_aux.py:28-29`, `python/train/sensor_aux.py:239-254`). Dirt is not in that list on purpose. A coarse `PROP` / `OBJECT` bucket is not added to either list. Build a three-way label from the full-resolution PNGs (the 12×16 aux grid is a feature target, not a driving mask, `python/train/sensor_aux.py:21-23`):

- `drivable` — pixel whose class name is on the paved allowlist **and** whose name was present in this recording’s `sem_classes.json`.
- `blocked` (semantic) — only after palette proof, a pixel whose class name a human copied from that same file. No name is added because it “sounds like” an obstacle.
- `unknown` — class 0, a name on neither list, a coarse bucket, or depth 0. Depth 0 is already invalid in the aux loader (`python/train/sensor_aux.py:69-84`). The centimetre scale is `depth_01 * far * 100` and is documented as unverified (`python/data/raw_frames.py:589-610`).

**Geometric fallback (no fine classes required).** When the palette has no separate wall/tree/pole/barrier/curb/cone names, a depth point is `blocked` by the in-corridor height test (1) or by the edge band (3). Height is world frame. The corridor and the edge band are ego frame. They are not one comparison.

1. **Height, world frame.** Unproject the depth sample to a world point with the camera pose and the recorded intrinsics. `z_world` is that point’s world Z. `z_road` is the cross-sloped road surface at the point’s lateral offset: `z_road = z_center + slope_lat * d_lat`, where `z_center` is `RoadPoly.z` interpolated along the centerline at the point’s station (the same interpolation is already in `python/train/frame_quality.py:251-263`), `d_lat` is the point’s signed lateral offset from that centerline (ego x+ is right, same sign as `pack_road_edge`, `python/train/sensor_aux.py:205-206`), and `slope_lat` is the local cross-slope (crown or bank) from one of the two sources below. Centerline z alone is not enough: a 6% bank at 3 m lateral offset is 0.18 m, which would false-block. If neither slope source is available, the point stays `unknown`. In the corridor from (2), `h = (z_world - z_road)` and `clear_eps_m = 0.15` on every row. `pad(r)` is the depth pad defined in the next paragraph. On the edge-z path, label `blocked` only when `h > clear_eps_m + pad(r)`, `drivable` only when `h <= clear_eps_m - pad(r)`, and everything in between `unknown` and out of the loss. On the depth-fit fallback those tests add `fit_tol` (defined with that fit): `drivable` only when `h <= clear_eps_m - pad(r) - fit_tol`, `blocked` only when `h > clear_eps_m + pad(r) + fit_tol`, otherwise `unknown`. A pad must never turn a real obstacle into `drivable`. Crown, banking, and speed bumps must stay under 0.15 m relative to that cross-sloped `z_road`, or they leave the `drivable` band (`blocked` only if `h > clear_eps_m + pad(r)`). PR #224 must meet: (a) a crowned road (2% cross-slope, 3.5 m lanes) has 0 blocked cells in-corridor; (b) a banked road (6% bank) has 0 blocked cells in-corridor; (c) where `pad(r) <= 0.02` m, a 0.10 m speed bump spanning the lane is not blocked in-corridor (`h = 0.10 <= 0.15 - pad(r)`, since `pad(r) <= 0.02` leaves `0.15 - pad(r) >= 0.13`); (d) on the edge-z path, where `pad(r) <= 0.02` m, a 0.10 m curb face just outside the corridor edge is `blocked` by the edge band (`0.10 >= 0.08 + pad(r)`); on the depth-fit fallback nothing below `thr + pad(r) + fit_tol` is ever `blocked` (it is `unknown`); (e) a 0.05 m lip outside the edge is not blocked; (f) where `pad(r) <= 0.02` m and `slope_lat` comes from `left_z`/`right_z`, a 0.10 m curb in the edge band is `blocked`; on the depth-fit path that curb is `unknown` and never `drivable`, because `fit_tol` lifts the blocked bar above 0.10 m; (g) on main, `pad(27.4) = 0.0287` m and `pad(30) = 0.0309` m. A 0.16 m object at 30 m is never `drivable`: `drivable` needs `h <= 0.15 - 0.0309 = 0.1191`, and both `0.16` and the low side `0.16 - 0.0309 = 0.1291` are above `0.1191`. It is `unknown` on main, because `0.16 < 0.15 + 0.0309 = 0.1809`. On wide, `pad(27.4) = 0.0791` m and `pad(30) = 0.0861` m, so `drivable` needs `h <= 0.15 - 0.0861 = 0.0639`, and `0.16` is not. (h) On the depth-fit path a 0.16 m object with a 0.05 m plane bias is never `drivable` at the ranges in the table under that fit. Missing `z_road` stays `unknown`.

   `r` is the view-Z depth-ray range in metres (`depth_cm / 100` from the uint16 centimetre PNG, `python/data/raw_frames.py:609-610`). Domain `r ∈ (0, far_m]` with `far_m = 300` for `main` and `wide` (`config/cameras.yaml`). Depth 0 is `unknown` and is not a value of `r`. Let `α_v = fov_v / H` and `α_h = fov_h / W` be that camera’s full-pixel angles in radians, with `fov_h = 2 atan(tan(fov_v/2) · W/H)`. Rounding view-Z to the nearest centimetre moves the point by at most 0.005 m. Snapping to the pixel-center ray misses the true ray by at most half a pixel, a transverse `r · hypot(tan(α_h/2), tan(α_v/2))`. `pad(r) = min(0.25, 0.005 + r · hypot(tan(α_h/2), tan(α_v/2)))`. So `pad(r) ≥ 0` and `pad(r) ≤ 0.25` on the whole domain. The cap binds on main at the far plane: `0.005 + 300 · 8.6480×10⁻⁴ = 0.2644`, so `pad(300) = 0.25`. Main is `fov_v = 34°`, `640×480`: the hypot factor is `8.6480×10⁻⁴`, and `pad(17.34) = 0.005 + 17.34 · 8.6480×10⁻⁴ = 0.019996 ≤ 0.02`, while `pad(17.35) = 0.020004 > 0.02`. So `pad(r) ≤ 0.02` m for `r ≤ 17.34` m on main. Wide is `fov_v = 88.7°`, `640×360`: the hypot factor is `2.7033×10⁻³`, and `pad(5.54) = 0.005 + 5.54 · 2.7033×10⁻³ = 0.019976 ≤ 0.02`. So `pad(r) ≤ 0.02` m for `r ≤ 5.54` m on wide. Acceptance (c), (d), and (f) use that interval. On the edge-z path, a 0.10 m curb is `blocked` there. On the depth-fit fallback, nothing below `thr + pad(r) + fit_tol` is ever `blocked` (it is `unknown`). Where `pad(r) > 0.02` m (main `r > 17.34` m, wide `r > 5.54` m) the curb label is out of scope and the cell is `unknown`. Runtime must never treat `unknown` as clear or `drivable`.

   The primary `slope_lat` source is the raw road-network edge left/right xyz on each `get_road_edges` record (`python/debug/gt_geom.py:226-230`). `RoadPoly` today stores only centerline xy, `width_m`, and centerline z (`python/debug/gt_geom.py:20-30`). `parse_road_edges` averages left/right z into that centerline and drops the per-edge values (`python/debug/gt_geom.py:248-251`). Keep those heights as new `RoadPoly` fields `left_z` / `right_z` (one value per centerline vertex, `None` where that edge had no height) instead of averaging them away; `road_dump` and `road_loader` must carry the fields (`python/collect/road_dump.py`, `python/collect/road_loader.py:67-98`, which re-parse through `parse_road_edges`). A per-side slope from that side’s edge z and `z_center` can represent a crown; a single bank is one slope. `slope_lat` on a side is `(edge_z - z_center) / (signed half-width)`, with the signed half-width positive on the right, so positive `slope_lat` raises the ego-right side. PR #224 commit `95ac7cf` does not read edge z: it uses `getattr(road, "cross_slope", None)` (`_cross_slope` in `python/train/obstacles.py`), a field `RoadPoly` does not have, and otherwise fits a per-side ordinary least-squares plane through the centerline from in-corridor points already within `clear_eps_m` of that centerline (minimum 3 points). #224 must use `left_z` / `right_z` as this primary source, not `cross_slope`.

   When `left_z` / `right_z` are missing at that station, the fallback is one per-side fit on a station window, and the label comes after the fit. The BEV cell is `(32/64) = 0.5` m lateral by `(40/64) = 0.625` m along-track (the 64×64 grid below). One side of a 3.5 m lane is 1.75 m, so the in-corridor cell centers on that side are 0.25, 0.75, 1.25, and 1.75 m: 4 cells. One row holds 4 cells per side, and `4 < 20`, so 20 inliers cannot come from one station row. The window is 5 consecutive along-track rows centered on the point’s row (5 × 0.625 m = 3.125 m), clipped at the grid ends. That window holds `5 × 4 = 20` cells per side. The minimum after the refit is 20 inliers, so the window can hold the count and one row cannot. Order, and this order only: (1) seed with paved-allowlist cells (`DRIVABLE_CLASS_ALLOWLIST` at `python/train/sensor_aux.py:29`) that are inside the corridor, inside the window, and not in the 0.5 m edge band, and whose `|h_centerline| <= 0.05` m, where `h_centerline` is height above centerline `z` before any slope; (2) fit a slope through those seeds and the centerline; (3) drop seeds whose residual is `> 0.05` m; (4) refit once on what remains; (5) then label. A 0.10 m curb is not a seed (`0.10 > 0.05`). Do not drop a cell because it is already blocked. That label does not exist yet. After the refit, a side with fewer than 20 inliers, or with no seed, has no `slope_lat` and the point stays `unknown`. Clipping the window at `y = 0` or `y = 40` can leave fewer than 20 cells; that side stays `unknown` too. The plane is pinned through the centerline, `h_hat = s * d_lat`. A seed has `|h_centerline| <= 0.05` m and an inlier has residual `<= 0.05` m, so `|s * d| <= 0.10` m at every inlier. The 5×4 window’s outer center is 1.75 m, so the plane there is at most 0.10 m above the centerline. Seeds at 0.25, 0.75, 1.25, and 1.75 m all at +0.05 m give the ordinary-least-squares slope `s = 0.05 * 4.00 / 5.25 = 0.03810`, and `s * 1.75 = 0.0667` m, inside that 0.10 m bound. The edge band continues 0.5 m past that outer inlier. The steepest inlier slope is `0.10 / 1.75`, so the plane at 2.25 m is at most `0.10 * 2.25 / 1.75 = 0.1286` m. `fit_tol = 0.13` m, above that bias. On this fallback path only, with `thr` equal to `clear_eps_m` in the corridor and `curb_eps_m` in the edge band: `drivable` iff `h <= thr - pad(r) - fit_tol`, `blocked` iff `h > thr + pad(r) + fit_tol`, otherwise `unknown`. The edge-z path does not add `fit_tol`. In the corridor the drivable bar is `0.15 - pad(r) - 0.13 = 0.02 - pad(r)`. It is negative wherever `pad(r) > 0.02` m (main `r > 17.34` m, wide `r > 5.54` m). On the edge band it is `0.08 - pad(r) - 0.13 = -0.05 - pad(r)`, negative on the whole domain. A negative bar has no `drivable` label: the cell is `unknown` unless it clears the blocked bar, and it is never `drivable`. PR #224 must add this same `fit_tol` on the depth-fit path if it moves from a constant 0.25 pad to `pad(r)`.

2. **Corridor, ego frame.** The corridor is the ego xy within the half-width of the center. When painted `lane_gt` is valid, the center is the painted center and the half-width is half the painted lane width. Otherwise the half-width is `road_width_m / 2` and the center is `-road_offset_m + y * sin(heading)`, the same construction as `pack_road_edge` (`python/train/sensor_aux.py:203-208`). Missing painted center and missing road width stays `unknown`.
3. **Edge band, outside the corridor.** A point laterally within `edge_band_m = 0.5` m outside the corridor edge from (2) uses `pad(r)` with `curb_eps_m = 0.08`. Where `pad(r) <= 0.02` m (main `r <= 17.34` m, wide `r <= 5.54` m), label `blocked` when `h >= curb_eps_m + pad(r)`. A 0.10 m curb is `blocked` on that interval, because `0.10 >= 0.08 + pad(r)` whenever `pad(r) <= 0.02`. Label `drivable` there only when `h <= curb_eps_m - pad(r)` (or the point is clear of the band). The open interval between those two thresholds is `unknown` and out of the loss. Those two edge-band comparisons are the edge-z path. On the depth-fit path they add `fit_tol`: `blocked` only when `h > curb_eps_m + pad(r) + fit_tol`, `drivable` only when `h <= curb_eps_m - pad(r) - fit_tol`. That drivable bar is negative on the whole domain, so a depth-fit edge-band cell is never `drivable`. Where `pad(r) > 0.02` m the curb label is out of scope and the cell is `unknown`. Runtime must never treat `unknown` as clear or `drivable`. `curb_eps_m` and `edge_band_m` are recorded on every `obstacles.jsonl` row next to `clear_eps_m`. On the edge-z path, this is how normal curbs get labeled until a semantic curb source is proven, and only where `pad(r) <= 0.02` m. On the depth-fit fallback, nothing below `thr + pad(r) + fit_tol` is `blocked` (it is `unknown`).

`height_coverage` also reads `RoadPoly.z` (`python/debug/gt_geom.py:305`), and the comment at `python/debug/gt_geom.py:26-29` is only the field note. A `PROP`/`OBJECT` id is not itself blocked.

**Clearance.** For blocked pixels only, unproject with the recorded intrinsics and the `cameras.yaml` pose (same projection family as `lane_contact_sheet`). Nearest distance is the minimum range whose foot lies within 0.5 m of the painted center polyline (`lane_gt` centers at 5/10/20/30 m, `python/debug/lane_targets.py:19-22`). If the 5 m and 10 m center slots are invalid, clearance is masked. Do not invent a straight corridor.

**Storage.** `obstacles.jsonl`: `{t, cam, grid_h, grid_w, x_min, x_max, y_min, y_max, mask, mask_src, clear_eps_m, curb_eps_m, edge_band_m, clear_m, clear_valid}` where `mask` is row-major `0=unknown, 1=drivable, 2=blocked` on a fixed BEV grid (64×64, x ∈ [-16, 16] m, y ∈ [0, 40] m), `mask_src` is `sem` or `geom`, and `clear_eps_m` is `0.15`, `curb_eps_m` is `0.08`, and `edge_band_m` is `0.5` on every row. Full PNGs stay the raw record. Do not put this in `gt.jsonl`.

**Check.** For `mask_src=sem`, overlay the BEV class on `raw/main_sem`: every `blocked` cell must be an allowlisted id, every `unknown` cell must be absent from both lists. For `mask_src=geom` on the edge-z path, every blocked cell is either in the corridor with `h > clear_eps_m + pad(r)`, or outside that edge by at most `edge_band_m` with `h >= curb_eps_m + pad(r)` and `pad(r) <= 0.02` m. On the depth-fit path the same tests add `fit_tol` on both sides of the bar. A curb cell with `pad(r) > 0.02` m is `unknown`, not blocked. Every `drivable` cell has `h <= threshold - pad(r)` on the edge-z path, or `h <= threshold - pad(r) - fit_tol` on the depth-fit path (or is clear of the edge band and meets the corridor rule). A negative drivable bar is not `drivable`. A cell in the pad band is `unknown`, never `drivable`. Runtime must never treat `unknown` as clear or `drivable`. A `PROP`/`OBJECT` id is not required. Before trusting `clear_m`, one parked prop at a measured distance must agree within 1 m. If it does not, the depth scale is wrong and clearance stays masked.

**Weight.** CE on `drivable`/`blocked` only. Unknown is dropped via `where(mask)`, not `x*mask`: a product writes 0 through an unknown cell and can train a clear. Clearance is masked the same way, weight 0 until the prop check passes.

**Head.** New training-only conv on the main-sector stem, same attachment point as `aux_depth_head` (`python/train/scene_net.py:1573-1584`). Not exported. The live net does not grow.

**LiDAR / radar.** Off (`config/sensors.yaml:12-18`). Not a source for this batch. Point clusters are not the obstacle label and are not a cone source. Cones, poles, walls, and barriers stay blocked until palette proof.

### 3. Curbs and road edges

Painted `lane_gt` stays `tech_from_painted`: a lookahead with paint on only one side is NaN / mask 0, never a guessed width (`python/debug/painted_lanes.py:1-21`, `python/debug/lane_targets.py:178-233`). The collector writes that dict and does not write `curbs` (`scripts/collect_scene_lanes.py:2871-2884`).

**Road edge (mapped boundary, not paint, not a curb).** `get_road_edges` left/right become one median width; the widest node is treated as a junction flare and discarded (`python/debug/gt_geom.py:225-273`). `pack_road_edge` turns `road_offset_m`, `road_width_m`, and heading into left/right x at `LOOKAHEADS_M` and never touches `lane_gt` (`python/train/sensor_aux.py:181-236`). The opt-in `road_edge_head` already exists and is outside the default ONNX (`python/train/scene_net.py:1587-1590`, `python/train/scene_net.py:1304-1313`). Use that vector. Do not retarget it at the flare edges in this batch.

**Curbs.** The curb head wants two polylines of `LANE_POINTS` points (`LANE_POINTS = 16` at `python/train/scene_net.py:53`, `N_CURBS = 2` at `python/train/scene_net.py:54`, packed in `python/train/scene_net.py:678-682`). Nothing fills `tech["curbs"]`. The live draw shifts the outer painted lane by `EDGE_SHOULDER_M` (0.4 m, `python/perception/road_model.py:23`) and marks that line predicted, because nothing detects a kerb (`python/perception/road_model.py:198-214`). A semantic curb or guard-rail name is unproven until palette proof. After that proof, the label is the depth boundary of the allowlisted name, resampled to 16 ego xy points. If the palette has no such name, `curb_valid` stays 0. Do not copy `road_edge` into the curb slots or into `lane_gt`.

**Check.** Contact-sheet the road-edge xs. A unit test must fail if any `road_edge` value is written into a `lane_gt` slot. Curb overlay only after palette proof; otherwise the sheet shows no curb.

**Weight.** Point loss is masked smooth-L1 where `curb_valid > 0.5`. Validity is BCE, and it runs for every wanted curb row, so an all-zero mask teaches “no curb” (`python/train/scene_net.py:1233-1239`). That is a confirmed absence, not a stand-in for “not labeled yet.”

`--heads` defaults to `""`. Empty trains every name in `HEAD_NAMES`: lanes, curbs, objects, signs, lane_gt (`python/train/train_scene.py:268-270`, `python/train/cam_strip.py:26`, `python/train/cam_strip.py:72-76`, `python/train/scene_net.py:112`, `python/train/scene_net.py:1144-1149`). `curbs` is in `OUTPUT_FIELDS` and `HEAD_NAMES` (`python/train/scene_net.py:96-112`), so the curb head is not opt-in and a default run backprops it. Sibling losses are detached only when the wanted set, after removing optional `ctl` and `road_edge`, is exactly `{lane_gt}` (`python/train/scene_net.py:1292-1299`). `ctl` and `road_edge` are the opt-in names: `parse_heads` adds them only when `--heads` lists them (`python/train/cam_strip.py:27-32`, `python/train/cam_strip.py:73-84`), and the road-edge term runs only then (`python/train/scene_net.py:1304-1313`).

Until curb labels exist, do not train with an empty `--heads`. Pass an explicit list that omits `curbs`, or `--heads lane_gt` so the sibling-zero path applies. New heads (obstacle mask, stop-line scalar, cone slot) stay off the way `road_edge` does: they are not added to `HEAD_NAMES` or `OUTPUT_FIELDS`, they are constructed only behind an explicit flag, and their loss weight stays 0 with a clear valid mask until that label’s sidecar exists. They are not exported.

### 4. Cones

**Blocked until palette proof.** A separate cone class is unproven: no annotation palette is on hand, so this repo cannot show that BeamNG names cones on their own. `OBJECT_CLASSES` is `vehicle, car, truck, bus, pedestrian, bike` (`python/train/scene_net.py:62`). Inserting `cone` there would shift indices and break old checkpoints.

If a later `sem_classes.json` contains a name a human marks as a cone, the label is connected components of that id, median depth, ego xy, written to `cones.jsonl` `{t, cones:[{x,y}]}`. Components with invalid depth are dropped, not placed at a default range. The head, when added, is a new training-only slot, not a new `OBJECT_CLASSES` entry, and not in default ONNX. LiDAR blobs are not a cone label.

### 5. Vehicles, heading, brake lights

**Position and heading, companions only.** `TRAFFIC_CHUNK` reads `pos`, `vel`, `dir` for `gvd_traffic_0` and `gvd_traffic_1` every 0.5 s (`python/collect/control_log.py:68-79`, `python/collect/control_log.py:165-177`). Other rows store `traffic: null` (`scripts/collect_scene_lanes.py:71-72`, `scripts/collect_scene_lanes.py:3204`). Spawned companions are `etk800` (`python/collect/spawn_mix.py:1013-1025`). West-coast default count is 2; other maps default to 0 (`python/collect/spawn_mix.py:966-969`).

**Derivation.** Ego xy from `world_to_ego` (`python/collect/signal_labels.py:80-97`). Yaw is the traffic `dir` in that same frame. Speed is the horizontal `vel` magnitude. Class `car` (they are etk800s). On a null tick, `object_valid=0` for that slot. Do not interpolate a car. `unseen_s` may count time since the last real sample for that name and must not create a new box.

**Do not train size.** `_object_matrix` fills missing length/width with 4.5 m and 1.8 m (`python/train/scene_net.py:574-584`). Those defaults are not labels. Supervise x, y, yaw, speed only.

**Ambient traffic** is not in the probe. The spawn Lua already walks `be:getObjectCount` (`python/collect/spawn_mix.py:992-1000`). Extending the probe to every non-player vehicle’s `pos`/`vel`/`dir` is a recorder change, still without a class guess: model string if the object returns one, else `vehicle`, never `truck`/`bus`/`pedestrian`/`bike` from a missing field.

**Brake lights.** The player path already attaches `Electrics()` (`scripts/collect_scene_lanes.py:1092-1097`). That call needs a beamngpy vehicle handle (`python/control/actuate.py:872-889`). The whitelist maps beamngpy `brake_lights` and the Lua alias `brakelights` onto `veh.brakelights` (`python/collect/control_log.py:34`, `scripts/test_control_log.py:65-70`). Companions are not that handle: Lua `spawnNewVehicle` names them `gvd_traffic_*` (`python/collect/spawn_mix.py:1013-1025`) and the probe finds those names with `scenetree.findObject` (`python/collect/control_log.py:73-75`). `sensors.attach('electrics')` on that scenetree object is not the gate.

**IQU45 gate, one vehicle at a time.** Look up that `gvd_traffic_*` name in the current beamngpy vehicle map (`python/sensors/tech.py:1389-1395`). Do not call `_resolve_vehicle` (`python/sensors/tech.py:1368-1387`): a miss there becomes the player (`python/sensors/tech.py:1379-1384`). Connect the vehicle that matched the name with `_connect_vehicle` (`python/sensors/tech.py:1413-1419`), then attach Electrics.

- **PASS:** that named vehicle connects, the Electrics attach is accepted, and the poll contains a `brake_lights` key. A value of 0 is a pass (lights off). Store that value.
- **FAIL:** the name is missing, the connect fails, the attach fails, or the key is absent. The brake-light loss weight is 0. The row stores `null`, never `0`. A stored 0, or an all-zero valid mask, is a trained absence (`python/train/scene_net.py:1233-1239`).

Do not copy the ego lamp onto other boxes, and do not threshold red pixels. `OBJECT_FEAT` has no brake-light column (`python/train/scene_net.py:60`); the value lives on the row.

**Check.** Ego-frame xy versus `world_to_ego(pos)` within 0.5 m on rows where `traffic` is non-null. Heading versus `dir` within 5°. A null row must not score.

**Head.** Existing `objects` / `object_class` / `object_valid` (`python/train/scene_net.py:544-588`). Empty slots stay `object_valid=0` so they do not dominate the match loss.

## Risks

- **VRAM.** Depth and annotation on eight cameras, a full-res decoder, or a new default ONNX head will fight BeamNG on 11 GB. Main+wide and training-only heads are the cap. Live infer stays ≤4 GB fp32.
- **Label noise.** Nav median width is not a curb (`python/debug/gt_geom.py:261-265`). Perpendicular paint mixes stop bars and crosswalks. `near_junction` is the wrong junction label. Object size defaults (4.5×1.8) and a missing-intent→`follow` join would both teach a lie. Depth scale is unverified until the prop check. `train_gt` decode errors skip GT and keep the colour frame (`scripts/collect_scene_lanes.py:3654-3668`).
- **Class imbalance.** Most ticks have no stop bar, no cone, no light, and empty object slots. Loss is on valid slots only. Repeat junction approaches, stop-line rows, and blocked-obstacle rows the way `--balance` repeats curves, and keep those repeats inside one split.
- **Coarse semantics.** `sem_classes.json` may be one `PROP`/`OBJECT` bucket rather than separate wall, tree, pole, barrier, curb, and cone names. Those fine classes stay blocked until palette proof. The fallback is the geometric test in section 2: in-corridor and edge-band height tests with `pad(r)`. On the edge-z path, a 0.10 m curb is `blocked` only where `pad(r) <= 0.02` m (main `r <= 17.34` m, wide `r <= 5.54` m). On the depth-fit fallback, nothing below `thr + pad(r) + fit_tol` is `blocked` (it is `unknown`). Past that range on the edge-z path the curb cell is `unknown`, and runtime must never treat `unknown` as clear or `drivable`. On the edge-z path, that edge band is how normal curbs get labeled until a semantic curb source is proven. A missing road height leaves that tick unknown. Obstacle avoidance does not wait on fine class names.
- **Electrics on Lua traffic.** `gvd_traffic_*` are scenetree objects (`python/collect/control_log.py:73-75`, `python/collect/spawn_mix.py:1013-1025`). `sensors.attach('electrics')` on that object is a FAIL. The pass path is a per-name beamngpy lookup (`python/sensors/tech.py:1389-1395`) and `_connect_vehicle` (`python/sensors/tech.py:1413-1419`), never the player fallback in `_resolve_vehicle` (`python/sensors/tech.py:1379-1384`). FAIL stores `null` and loss weight 0, not a 0 that would train “lights off.”
- **Holdout leakage.** A time-tail split puts the same intersection in both sides. Use `--holdout-cells` (250 m cells, 50 m drop around them, `python/train/train_scene.py:333-339`). Join sidecars only inside the row’s own recording root. `impacts` / `settle` / `stall` are left out only with `--mask-events`, which is off by default (`python/train/train_scene.py:461-466`, windows in `python/train/event_mask.py:1-21`). They must not be the only source of “stopped at a light.”
